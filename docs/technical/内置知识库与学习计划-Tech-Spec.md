# 内置知识库与学习计划 MVP Tech Spec

日期：2026-09-09

状态：技术方案，待实现与验收。本文不代表资料已经入库或功能已经通过验证。

## 1. 技术结论与范围

沿用现有 Web 应用，以普通 Python 服务串联“检索内置资料 → 生成具体任务 → 校验引用 → 完整保存”。新计划使用 `rag_v1`，既有 `rule_v1` 计划保持原样。

- 产品依据：[PRD](../product/内置知识库与学习计划-PRD.md)、[PDD](../product/内置知识库与学习计划-PDD.md)。
- 交互依据：[学习计划 Demo](../product/学习计划-Demo.html)，以 PDD 的正式功能边界为准。
- 本轮完成内置资料导入、任务生成、依据快照、技能覆盖、导航及失败处理。
- 不增加上传页面、资料管理后台、学习问答、重生成、版本切换或个性化排期。
- LangChain/LangGraph、Redis 和独立任务队列保留为后续迭代，不作为本轮依赖。

| 部分 | 技术选择 | 职责 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite、现有 CSS | 报告入口、计划列表与详情、导航和任务状态 |
| 后端 | Python、FastAPI、Pydantic | 业务流程、结构校验和接口错误处理 |
| 业务存储 | SQLite、SQLAlchemy、Alembic | 计划、任务、引用快照和进度 |
| 资料处理 | pypdf、现有文本解析和分块模块 | 作者离线导入并审核指定 PDF |
| 检索 | FastEmbed、`BAAI/bge-small-zh-v1.5`、Chroma | 本地中文向量化和相关片段检索 |
| 生成 | 现有 DeepSeek 结构化客户端 | 根据片段生成具体任务和完成标准 |

## 3. 数据流与服务边界

```text
作者离线导入
PDF → 提取与人工核对 → 文本分块 → FastEmbed → Chroma
                         └→ SQLite 文档记录与导入状态

用户生成
报告 ID → 查询已有计划 → 读取优先技能快照
       → 按技能检索内置资料 → DeepSeek 生成候选任务
       → 校验任务与引用 → SQLite 单事务保存
       → 返回正式计划 → 查看依据与更新状态
```

`StudyPlanService` 负责流程和保存；检索服务返回候选片段；独立的学习任务生成组件负责提示词、输出校验和证据绑定。通过构造参数注入依赖，便于用替身测试异常场景。

本轮采用同步请求返回最终结果，FastAPI 同步端点在线程池执行现有阻塞客户端调用。生成期间前端显示加载状态，不使用流式正式计划，也不使用无持久化保障的后台任务承担生成。

外部调用期间不持有数据库写事务。先读取必要的报告快照并结束读取事务，再检索和生成；最终使用短事务重新核对报告与已有计划后写入。SQLAlchemy Session 不跨线程共享。

## 4. 内置资料导入与检索

### 4.1 导入方式

新增作者使用的命令行导入脚本，接收 PDF 路径；不新增用户上传入口。首批文件为 `AI-Agents-in-Depth-zh-CN.pdf`，原始位置见 PRD，不将个人绝对路径写死在应用中。

1. 用 pypdf 提取正文，检查空页、乱码、目录噪声和段落顺序；抽样核对 PDF 原文。
2. 仅做可追溯的空白与换行清理，不用模型改写参考原文；允许作者整理后再导入。
3. 复用分块器，以当前配置的 500 字符、80 字符重叠作为起点；结合实际片段调整，不能超过模型可用输入长度后静默截断。
4. 保存文档状态，完成向量写入与抽样检索后，才将该文档加入内置可检索范围。
5. 记录文件摘要、处理后文本摘要、嵌入模型及分块参数；相同输入与参数再次导入时复用已成功结果。

本轮使用独立的内置 Chroma collection，并由配置指定已审核、状态为 `ready` 的文档 ID。复用索引适配器，但不搜索现有通用知识库中的其他资料。查询时在向量检索前按允许的文档 ID 过滤，需要扩展现有索引查询端口；不能先查询全库再过滤 Top-K。

SQLite 与 Chroma 不具备跨库事务，沿用现有 `indexing → ready/failed` 导入状态与失败补偿。失败或未审核的文档不能进入生成范围；重试只处理对应失败导入，不覆盖已启用资料。索引残留的清理遵循工作区删除规则。

页码与章节不作为本轮必填项。第一版若只保留正文和来源名，就不展示定位；后续只有提取、分块、检索、快照全链路保留且核对后，才填入定位字段。PDF 物理页码与印刷页码必须区分。

### 4.2 检索与覆盖判断

- 沿用报告优先技能顺序，兼容历史字符串与当前技能对象；仅做去空和保序去重，不重新评估优先级。
- 每个技能分别查询，以技能原文为主体构造检索词；不把多项技能合成一个查询后宣称全部覆盖。
- 初始每项技能取 Top-5，沿用当前余弦距离上限 `0.45` 作为试验起点。距离越小越相关；该数值不是命中率或可信度承诺。
- 去掉空片段和重复片段，限制提交给模型的上下文大小；超出请求容量时明确返回容量错误，不能静默丢弃技能。
- 无合格片段时，该技能记为 `no_relevant_evidence`；有片段但不足以支持具体任务时，记为 `insufficient_support`。
- 配置缺失、内置文档未就绪、嵌入或索引异常属于服务失败，不能当成资料不足。

检索相似不等于原文支持。模型需判断片段能否支撑知识内容，后端验证引用来源，真实样例验收再人工核对语义支持。本文不声称结构校验可以证明任务正确。

## 5. 任务生成与校验

将有候选依据的技能及各自片段一次提交给现有结构化客户端。提示词包含任务规则、JSON Schema、技能顺序及以 `chunk_id` 标记的原文。资料正文作为参考数据，不能改变系统任务或触发工具操作。

模型按技能返回以下候选数据：

- `skill`、`support_status`：目标技能及是否有足够依据。
- 有依据时返回非空 `tasks`；每项包含 `phase`、`title`、`learning_content`、`action`、`completion_criteria`、`evidence_ids`。
- 依据不足时返回空任务与原因；不得用通用模板填充。

后端必须执行以下校验：

1. 每个提交的技能恰好出现一次，无新增或遗漏；有依据的技能至少有一项有效任务。
2. 任务字段非空且长度受限，`phase` 复用 `learn/practice/verify`；阶段可重复或缺省组合，不强制三项任务。
3. 每项任务至少有一个引用 ID，且全部属于该技能本次检索到的候选片段。
4. 资料名与原文由后端从候选片段填入，模型不得直接提供引用原文或页码。一个任务支持多条依据。
5. `position`、初始状态与到期日由后端计算。技能间保持报告顺序，技能内保持有效任务顺序。

原文支持的是知识内容，实践动作允许由模型设计，前端以“具体行动”独立展示，不能伪装成原文要求。

新提示词不要求每项技能固定任务数。复用当前可选截止日期及到期日分配函数，在全部有效任务确定后计算；未设置时均为 `null`，不宣称已根据学习时间进行个性化排期。

JSON 不合法时复用客户端已有的一次结构修复；不在服务外层叠加无限重试。未知引用、遗漏技能或修复后仍无效均作为生成失败，整个结果不保存。只有明确的资料不足允许部分覆盖，不能把生成错误包装成部分成功。

## 6. 持久化与旧数据兼容

继续使用 `study_plans` 和 `study_tasks`。通过 Alembic 新增可空字段，旧计划不回填虚构内容。

| 对象 | 新增或调整字段 | 约定 |
| --- | --- | --- |
| 计划 | `generation_method` | 新建为 `rag_v1`，旧值保持 `rule_v1` |
| 计划 | `coverage`，可空 JSON | 保存目标技能、已覆盖技能、未覆盖技能及原因 |
| 计划 | `generation_metadata`，可空 JSON | 记录实际模型、提示词版本和资料修订标识，供排查 |
| 任务 | `learning_content`、`action`，可空 Text | 新计划必填，旧任务保持空值 |
| 任务 | `evidence`，可空 JSON 数组 | 新任务非空；每项保存片段 ID、文档 ID、来源名、原文及可核对的可选定位 |
| 任务 | `resource_query` 改为可空 | 保留旧值，新任务不再生成资源搜索词 |

`coverage` 使用 `target_skills`、`covered_skills`、`uncovered_skills` 三部分；未覆盖项含 `skill` 和 `reason_code`。前两者保序，覆盖与未覆盖必须互斥且合并后等于全部目标技能；已覆盖技能必须与有效任务对应。

引用采用生成时的快照，不依赖读取时重新检索。文档 ID 作为追溯信息，不使用会随源文档删除而级联删除快照的关系。计划生成后修改资料，不改变既有任务与引用。

保留 `match_report_id` 唯一约束，以及任务位置唯一约束。计划、任务、覆盖信息、依据在同一 SQLite 事务中提交；失败整体回滚。不持久化空计划，也不保存“生成中”的正式计划。

进度继续由任务状态派生，不另存百分比。旧计划 `coverage=null` 表示未记录覆盖信息，不解释为全部覆盖或资料不足；按 `rule_v1` 展示“此计划由早期规则生成，未附参考原文”。新计划缺少必需依据属于数据错误，不能套用旧版提示。

迁移验证使用含旧计划的测试数据库副本，确认内容和进度保持不变。本轮实施不通过删除数据库重新建表替代迁移；回退涉及丢弃新增数据时应先备份并单独确认。

## 7. API、重复请求与失败处理

### 7.1 接口调整

所有路径沿用 `/api/v1` 前缀。

| 接口 | 本轮约定 |
| --- | --- |
| `POST /study-plans` | 请求仍为 `match_report_id` 和可选 `deadline`；首次保存返回 201，已有计划返回 200 与已有详情 |
| `GET /study-plans` | 新增精确 `match_report_id` 筛选，保留其他筛选与分页；核对结果时返回空数组表示暂未查到 |
| `GET /study-plans/{plan_id}` | 返回原有字段及新增内容、覆盖和引用快照 |
| `PATCH /study-tasks/{task_id}` | 沿用现有状态更新接口和状态机 |

按报告查计划必须由后端筛选，不能只在前端当前分页中查找。已有计划优先返回，忽略重试携带的不同截止日期，不覆盖原计划。报告不存在返回 404；仅对实际新建校验截止日期。

保留错误体的 `detail`，为本轮可区分的领域异常增加稳定的 `code`，可选 `uncovered_skills`。前端依据错误码选择文案，不解析英文错误字符串；其他接口不必同步改造。

| 状态 | HTTP / code | 处理 |
| --- | --- | --- |
| 无优先技能 | 409 / `NO_PRIORITY_SKILLS` | 不生成、不保存 |
| 全部资料不足 | 422 / `INSUFFICIENT_KNOWLEDGE` | 返回未覆盖技能，不创建空计划 |
| 部分资料不足 | 201 | 保存完整有效结果，明确展示未覆盖技能 |
| 检索不可用 | 503 / `KNOWLEDGE_UNAVAILABLE` | 系统失败，提供重试 |
| 生成无效或供应商失败 | 502 或 503 / `PLAN_GENERATION_FAILED` | 不降级到规则模板 |
| 后端调用超时 | 504 / `PLAN_GENERATION_TIMEOUT` | 核对是否已有结果，再决定重试 |
| 保存失败 | 500 / `PLAN_PERSISTENCE_FAILED` | 回滚；结果不确定时核对已有计划 |

### 7.2 并发与超时

入口先查询已有计划；最终写入前再次查询。并发请求仍可能同时调用模型，这是本轮可接受的成本边界。唯一约束决定只有一份计划能提交，发生对应唯一冲突时回滚并读取胜出的计划，返回 200；其他数据库错误不能误当作重复成功。

本轮不引入分布式锁。按钮禁用用于改善交互，数据库唯一约束负责最终一致性。不会通过清除已有计划来重试。

前端网络断开或请求超时不能断言后端未保存。先调用按报告查询接口：查到则打开；暂未查到则显示“暂未确认生成结果，请重试查看”；允许用户再次核对或重试生成，重复生成仍受唯一约束保护。查询失败时保留未知状态。

沿用现有客户端超时与有限重试，但实施时需核对 HTTP 单次超时、重试和 JSON 修复的累计等待，并设置整次生成的明确时间预算。单次 30 秒配置不等于整条流程最多 30 秒；前端或代理更早超时仍按未知结果处理。服务总预算耗尽后不再启动新调用或进入保存阶段，记录失败阶段供排查。

## 8. 前端实现约定

复用匹配报告页、学习计划列表与详情，在现有侧边栏增加可展开的学习计划子菜单，不引入新路由库或全局状态库。

- 报告页按报告 ID 查询计划，决定显示“生成”或“查看”；生成成功后以返回的计划 ID 导航。
- 当前报告上下文由报告页面或计划详情的真实 `match_report_id` 确定；直接打开详情与刷新时也可恢复。
- 切换报告后重新读取其计划状态，忽略上一份报告的迟到响应；没有报告上下文时先打开计划列表。
- 菜单展开状态与页面选中状态分开处理；收起不切换页面，详情打开时自动展开并高亮当前计划。
- 详情按技能分组，展示具体内容、行动、完成标准和默认收起的依据；覆盖比例与任务完成比例分别计算。
- 沿用任务状态机和保存后更新策略，失败保留上次成功状态与进度；旧任务从已完成只能回到进行中，UI 不提供非法转换。

菜单与引用使用可键盘操作的按钮或原生展开控件，提供展开状态。窄屏保持单列。模型内容和资料原文按文本渲染，不注入 HTML。Demo 场景选择器、模拟数据和版本占位入口不进入正式页面。

## 9. 配置、日志与运行边界

复用 `DATABASE_URL`、`LLM_*`、`RAG_CHROMA_PATH`、`RAG_EMBEDDING_MODEL`、分块及距离配置。新增内置 collection、允许的文档 ID、生成上下文上限和总时间预算配置；参数具体值在真实资料试跑中记录，不当作质量保证。

模型与 collection 配置须匹配：更换嵌入模型或分块策略时创建新的索引修订并重新导入，验证后再切换；不能直接混用不同向量空间。

日志记录请求 ID、报告 ID、阶段、耗时、检索数量、覆盖结果、实际模型与错误类别。不要默认输出完整简历、资料正文或 API Key；提示词仅发送完成该任务需要的技能与资料片段。

本轮按本地或单实例 MVP 运行。同步生成可能占用工作线程，不能据此宣称支持高并发；若真实耗时或并发超出可接受范围，再实施持久任务队列。

## 10. 实施顺序与验收

按以下独立、可验证的改动推进，每步检查后单独提交：

1. 迁移与响应契约：新增字段、旧计划兼容、按报告查询和错误码。
2. 内置资料：导入脚本、来源隔离、失败恢复和真实片段核对。
3. 生成服务：提示词、覆盖判断、引用绑定、原子保存与重复请求。
4. 前端流程：报告入口、菜单、详情依据、状态与超时核对。
5. 真实验收：使用少量真实报告、指定资料、实际嵌入模型和 DeepSeek，完成浏览器流程。

验证重点：

- 单元测试：顺序、部分与全部资料不足、检索异常、未知引用、遗漏技能、非法输出及状态转换。
- API 与数据库测试：201/200 行为、按报告筛选、唯一冲突、保存回滚、刷新后快照不变、旧计划迁移与状态更新。
- 索引测试：只命中允许的内置文档、导入重试不重复启用、未就绪或失败文档不可检索。
- 前端检查：运行现有 lint 与构建；浏览器验证报告切换不串数据、引用展开、失败保留状态及超时核对。
- 真实质量检查：人工核对引用来自 PDF 且支持任务知识内容；记录覆盖与未覆盖技能、任务可执行性和实际耗时。

实施时优先扩展现有 `test_study_plan.py`、`test_study_plans_api.py` 及检索相关测试。模拟客户端测试不能证明真实模型、检索质量或浏览器流程可用；验收记录需区分自动测试、真实服务调用和人工原文核对。无需先建设完整评测集或固定命中率门槛。

## 11. 后续迭代

以下技术只在需求出现后评估，不在本轮预先搭建：

- LangChain/LangGraph：当流程需要多步工具选择、分支恢复或复杂 Agent 状态时评估。
- Redis：当出现多实例共享缓存、限流或协调需求时评估；不代替关系数据库保存正式计划。
- 独立任务队列：当生成耗时、并发或断线恢复需要后台可靠执行时，引入持久任务状态、重试和结果查询。
- PostgreSQL：多人部署与写入并发增长后评估迁移。
- 混合检索或重排：真实样例证明当前检索不足时再引入，先区分资料缺失与检索失败。
- 产品扩展：用户资料、学习问答、计划版本管理与个性化排期另写方案，遵循 PRD 的后续范围。
