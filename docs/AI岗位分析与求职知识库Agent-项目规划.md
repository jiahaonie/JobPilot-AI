# AI 岗位分析与求职知识库 Agent

## 1. 项目定位

项目暂定名：**JobPilot AI**。

这是一个面向求职者的 AI 应用。用户可以录入岗位 JD、上传个人简历和学习资料，系统负责解析岗位要求、分析技能差距、基于资料回答问题，并生成可执行的学习计划。

这个项目不是简单的“聊天机器人”，而是一个包含后端 API、数据库、RAG、Agent 工具调用、评测、测试和部署的完整 AI 应用。主要用于申请以下实习岗位：

- AI 应用开发实习生
- 大模型应用开发实习生
- RAG 开发实习生
- AI Agent 开发实习生
- Python AI 后端实习生
- 智能体平台开发实习生

## 2. 项目解决的问题

普通求职者面对岗位描述时，经常存在以下问题：

1. 不清楚 JD 中哪些是硬性要求，哪些只是加分项。
2. 很难客观判断自己的技能与岗位要求之间的差距。
3. 收集了很多学习资料，但无法快速定位与当前岗位相关的内容。
4. 学习计划容易过于笼统，缺少优先级和可验证的完成标准。
5. 同时投递多个岗位后，无法系统整理岗位、公司和准备进度。

JobPilot AI 的目标，是把“岗位理解—能力分析—资料检索—学习计划—投递跟踪”连接成一个完整工作流。

## 3. 项目边界

### 第一版要做

- 用户注册与登录，或者先实现单用户模式。
- 手动粘贴岗位 JD，保存岗位信息。
- 上传 PDF、Markdown、TXT 格式的简历和学习资料。
- 将 JD 解析为结构化字段。
- 将个人技能与岗位要求进行匹配。
- 基于学习资料进行带引用的 RAG 问答。
- 生成分阶段学习计划。
- 保存岗位、分析结果、学习任务和投递状态。
- 提供 REST API、自动化测试和 Docker 启动方式。

### 第一版不做

- 不自动爬取 BOSS 直聘，避免违反平台规则和增加反爬复杂度。
- 不做自动投递、自动联系招聘者等高风险外部操作。
- 不承诺“AI 能准确判断是否会被录用”。
- 不一开始就做复杂多 Agent 编排。
- 不把 UI 美化放在后端和核心 AI 流程之前。

## 4. 用户使用流程

1. 用户创建个人技能档案。
2. 用户复制并保存一个岗位 JD。
3. 系统提取岗位名称、技能要求、经验要求、学历要求和加分项。
4. 系统根据用户简历和技能档案生成匹配分析。
5. 用户查看缺失技能及对应原文证据。
6. 用户上传课程笔记、官方文档等学习资料。
7. 系统基于资料回答问题，并返回文档名、章节和文本片段。
8. Agent 根据技能差距调用工具生成学习任务。
9. 用户更新任务和投递状态，形成完整求职记录。

## 5. 核心功能设计

### 5.1 岗位管理

字段建议：

- 公司名称
- 岗位名称
- 城市和区域
- 实习时间要求
- 岗位原始文本
- 岗位来源链接
- 投递状态
- 创建时间和更新时间

投递状态可以设计为：`待分析`、`准备中`、`已投递`、`已沟通`、`面试中`、`已结束`。

### 5.2 JD 结构化解析

通过 LLM 结构化输出，将 JD 转换为 Pydantic 模型：

```python
class JobRequirement(BaseModel):
    job_title: str
    required_skills: list[str]
    preferred_skills: list[str]
    education: str | None
    internship_duration: str | None
    responsibilities: list[str]
    evidence: list[str]
```

必须保留原文证据，避免模型凭空添加岗位要求。解析失败时，应保存原始 JD，并允许重新解析。

### 5.3 简历与岗位匹配

不要只输出一个无法解释的“匹配度 85%”。建议拆成：

- 已满足的核心技能
- 部分满足的技能
- 尚未体现的技能
- 简历中存在但岗位未要求的技能
- 最优先补齐的三项能力
- 每项判断对应的 JD 和简历证据

如果后续需要总分，应公开评分规则，例如：硬技能 50%、项目经历 25%、工程能力 15%、其他要求 10%。该分数只能代表项目内部规则，不能解释为真实录用概率。

### 5.4 RAG 知识库

知识库主要存放：

- Python、FastAPI 学习笔记
- RAG 和 Agent 学习资料
- 官方技术文档
- 自己整理的面试题
- 项目设计与故障记录

基本数据流：

```text
上传文档
  -> 文档解析
  -> 清洗与分块
  -> Embedding
  -> 向量库与元数据存储
  -> 用户提问
  -> 查询改写
  -> 召回候选片段
  -> 重排与阈值过滤
  -> LLM 生成回答
  -> 返回答案与引用
```

建议先实现向量检索，再增加关键词与向量混合检索。回答缺少可靠证据时，应明确表示资料库中没有足够信息，而不是编造答案。

### 5.5 Agent 工具

第一版实现 3～5 个工具即可：

- `get_job_requirements(job_id)`：读取结构化岗位要求。
- `compare_resume_with_job(job_id, resume_id)`：生成技能差距分析。
- `search_learning_material(query, filters)`：检索学习资料。
- `create_study_plan(job_id, deadline)`：生成学习计划。
- `update_application_status(job_id, status)`：更新投递状态。

每个工具必须包含参数校验、权限检查、错误返回和日志。Agent 不应直接拼接 SQL，也不能未经确认执行高风险外部操作。

### 5.6 MCP 服务

后续可以使用 [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk)，把岗位查询、资料检索和学习计划能力暴露为 MCP Tools 或 Resources。

MCP 是项目的加分项，不应为了使用 MCP 而重复实现已有 REST API。建议先完成稳定的业务服务层，再让 FastAPI 路由和 MCP 工具共同调用该服务层。

## 6. 推荐架构

```text
app/
├── api/                 # FastAPI 路由
├── core/                # 配置、日志、安全和异常
├── models/              # SQLAlchemy 数据模型
├── schemas/             # Pydantic 请求与响应模型
├── repositories/        # 数据访问层
├── services/            # 岗位、简历、知识库业务逻辑
├── llm/                 # 模型客户端、提示词、结构化输出
├── rag/                 # 解析、分块、检索、重排、引用
├── agents/              # Agent 编排和工具定义
├── mcp_server/          # MCP 服务入口
└── main.py              # FastAPI 应用入口
tests/
├── unit/
├── integration/
└── evaluation/
```

关键原则：API 层只处理 HTTP 请求；业务逻辑放在 service；数据库访问放在 repository；模型和 RAG 组件可以独立替换和测试。

## 7. 推荐技术栈

- Python 3.11 或 3.12
- FastAPI、Uvicorn、Pydantic
- SQLAlchemy 2.x、Alembic
- 开发阶段使用 SQLite，完善后切换 PostgreSQL
- 向量存储可选 Qdrant、Chroma 或 pgvector
- LLM API 使用兼容 OpenAI 风格的客户端封装
- pytest、pytest-asyncio、FastAPI TestClient 或 HTTPX
- Docker、Docker Compose
- Ruff 或 Black、mypy 可作为工程质量工具
- 前端第一版使用 Streamlit，或者仅提供 Swagger 和简单演示页面

## 8. 数据库实体建议

- `users`：用户信息。
- `resumes`：简历元数据和解析结果。
- `jobs`：岗位原文和基本信息。
- `job_requirements`：结构化岗位要求。
- `match_reports`：匹配分析及证据。
- `documents`：知识库文档。
- `document_chunks`：文档分块与向量关联。
- `study_plans`：学习计划。
- `study_tasks`：可执行任务。
- `applications`：投递状态和备注。
- `llm_traces`：模型、耗时、Token、失败原因等观测数据。

## 9. 安全与可靠性

- 简历和 JD 都属于不可信输入，需要防范 Prompt Injection。
- 不允许上传可执行文件。
- 设置文件大小、类型和页数限制。
- API Key 只能放在环境变量中，不能提交 Git。
- 日志中不要记录身份证号、手机号和完整简历正文。
- 模型输出必须通过 Pydantic 校验。
- Agent 工具应使用允许列表，限制参数和执行范围。
- 模型超时、限流和 JSON 解析失败都应有明确异常处理。

## 10. 测试计划

### 单元测试

- JD 字段解析和清洗。
- 文档分块边界。
- 匹配评分规则。
- 工具参数校验。
- 引用格式生成。

### 集成测试

- 创建岗位到生成匹配报告的完整流程。
- 上传文档到成功检索的完整流程。
- 数据库事务和回滚。
- LLM 客户端使用 Mock，避免测试依赖真实付费 API。

### AI 评测

建立脱敏的小型评测集，例如：

- 20～50 条岗位 JD。
- 10～20 份虚构或脱敏简历。
- 30～50 个资料问答问题。
- 每个问题标注相关文档片段。

可记录指标：

- 检索 Recall@K、MRR。
- 引用命中率。
- 结构化输出成功率。
- 工具调用成功率。
- API P50/P95 延迟。
- 单次请求 Token 和成本。

只有真正执行评测后，才能将结果写入 README 和简历。

## 11. 开发阶段规划

### 阶段一：后端基础，约 4～6 天

- 初始化项目、配置和日志。
- 完成岗位 CRUD。
- 完成数据库模型、迁移和测试。
- 提供 OpenAPI 文档。

验收标准：岗位数据能够通过 API 创建、查询、修改和删除，测试通过。

### 阶段二：LLM 结构化解析，约 3～5 天

- 封装模型客户端。
- 使用 Pydantic 定义结构化结果。
- 实现 JD 解析和失败重试。
- 保存证据和模型调用记录。

验收标准：对一组脱敏 JD 进行解析，结果可追溯到原文。

### 阶段三：RAG，约 6～8 天

- 文档上传、解析和分块。
- Embedding 和向量检索。
- 带来源引用的问答。
- 增加检索评测。

验收标准：回答能够返回引用；无证据时拒绝编造。

### 阶段四：Agent 工作流，约 5～7 天

- 实现岗位、匹配、检索和计划工具。
- 完成 Agent 路由与工具调用。
- 记录工具调用轨迹和失败原因。

验收标准：系统能够根据用户目标选择正确工具，并处理工具失败。

### 阶段五：工程化与展示，约 4～6 天

- Docker Compose。
- 完善 pytest 和 GitHub Actions。
- 编写 README、架构图和演示脚本。
- 可选：增加 Streamlit 页面和 MCP 服务。

验收标准：陌生人按照 README 可以启动；演示流程可以稳定复现。

## 13. 简历写法

完成 MVP 后可以写：

> 独立开发基于 FastAPI、RAG 与工具调用的 AI 岗位分析助手，实现 JD 结构化解析、简历技能匹配、带来源引用的知识库问答及学习计划生成；使用 SQLAlchemy 完成岗位与任务持久化，通过 pytest 覆盖核心业务流程，并使用 Docker 提供可复现部署环境。

完成评测后可以追加：

> 构建 XX 条脱敏评测数据，对检索 Recall@K、引用命中率、工具调用成功率和接口延迟进行评估；根据真实结果优化分块、召回和重排策略。

`XX` 和指标必须替换为实际数据。不能把 MCP SDK、向量数据库或开源组件描述成自己从零研发。

## 14. 面试准备问题

1. 为什么选择 RAG，而不是把所有资料直接放进 Prompt？
2. 文档如何分块？块大小变化会带来什么影响？
3. 如何证明检索结果真的相关？
4. 为什么 API、业务逻辑和数据库访问要分层？
5. 模型返回不符合 JSON Schema 时如何处理？
6. Agent 如何选择工具？调用失败如何恢复？
7. 如何避免简历文本中的 Prompt Injection？
8. 为什么不直接让模型计算一个匹配百分比？
9. 如何控制 Token、延迟和 API 成本？
10. 如果替换模型或向量数据库，需要修改哪些模块？

## 15. 项目所有权检查

准备投递前，至少能够做到：

- 画出一次请求的完整数据流。
- 解释每一层的职责。
- 修改一个岗位字段并完成数据库迁移。
- 更换分块参数并预测检索结果变化。
- 故意制造一次模型超时或结构化输出错误，并完成诊断。
- 为一个新 Agent 工具编写参数模型、业务逻辑和测试。
- 不借助 AI，独立讲清楚自己编写和改造的部分。

## 16. 开源与真实性说明

GitHub Trending 只代表一定时期内的社区关注度，不代表项目自动具备简历价值。真正的简历价值来自完整业务闭环、可解释的数据流、真实测试结果和个人可证明的贡献。
